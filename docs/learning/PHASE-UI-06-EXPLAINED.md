# UI-06 — مراجعة الواجهة والتحقق

التاريخ: 2026-10-20. الحالة: المراجعة المحلية مكتملة؛ اختبار الواجهة الحي ومراجعة المطوّر معلقان.

## ماذا راجعنا؟

راجعنا واجهة إدارة المساعدين والملفات الموجودة، دون إضافة ميزات أو تغيير Backend. ترتبط المراجعة بـ FR-001–003 وAC-001–007/018. الاختبارات المحلية تستخدم استجابات مضبوطة؛ نجاحها لا يثبت اتصال الواجهة الحقيقي بـ Supabase.

## الملفات والمسؤوليات

- `frontend/src/app/routes.tsx`: يربط URL بالشاشة داخل المسار المحمي. أضفنا index redirect من `/assistants/:id` إلى `configuration` حتى لا يرى المستخدم هيكلًا فارغًا. `replace` يتجنب إضافة محطة تحويل غير مفيدة إلى سجل التنقل.
- `frontend/src/assistants/Assistants.tsx`: يعرض قائمة المساعدين وإعداداتهم؛ صححنا ترميز علامات الحذف في رسائل التحميل فقط.
- `frontend/src/knowledge/KnowledgeFiles.tsx`: يدير حالات الملفات والتأكيد والطلبات. يحتفظ `removeTrigger` بزر الإزالة الذي بدأ العملية، و`filesHeading` بعنوان القائمة. الإلغاء يعيد التركيز للزر، والنجاح ينقله للعنوان لأن صف الملف سيختفي. لا ننقل التركيز عند فشل الطلب أو مغادرة الشاشة.
- `frontend/src/knowledge/api.ts`: يبني طلبات الملفات باستخدام جلسة المالك الحالية. لم نغيّر عقده. تبقى حدود النوع والحجم في الواجهة مساعدة للمستخدم، بينما Backend هو المرجع الأمني.
- `frontend/tests/browser/review.spec.ts`: ثلاثة اختبارات للعنوان المباشر، نص التحميل، والتنقل بلوحة المفاتيح عند عرض 320px مع اسم ملف طويل وإلغاء/إتمام الإزالة.

## تتبع إزالة ملف

المستخدم يختار Remove ثم Confirm removal. تستدعي `FileManager.run` دالة الإزالة في `knowledgeApi` مع جلسة المستخدم؛ يصل DELETE إلى `remove_file` في `backend/src/assistant_builder/knowledge_api.py`. يتحقق Backend من المالك ثم يستدعي `KnowledgeService.remove` في `knowledge_service.py` عبر transaction وrepository وحدود RLS الموجودة. بعد 204 تعيد الواجهة تحميل القائمة وتعرض رسالة وتنقل التركيز للعنوان. الإزالة تفصل الملف عن المسودة؛ لا تعني حذف Storage فورًا.

إذا ضاع الرد بعد نجاح الخادم، لا نكرر DELETE أو upload تلقائيًا. نعيد قراءة القائمة أولًا. إذا فشلت القراءة تصبح القائمة غير مؤكدة وتُمنع العمليات حتى Refresh ناجح. لا نسمح لنتيجة طلب قديم بإظهار ملفات مالك سابق بعد تبديل الحساب.

## القرارات والحدود

استخدمنا refs الموجودة في React بدل مكتبة جديدة لإدارة التركيز. احتفظنا بتأكيد الإزالة داخل الصفحة بدل إعادة تصميمه كـ dialog. روابط التنزيل مؤقتة وموجودة في الذاكرة؛ لا تُرفق بها Authorization عند فتحها. مفاتيح Storage المميزة تبقى في الخادم. هذه المراجعة لم تعدل RLS أو Auth أو قاعدة البيانات.

## الاختبار والتشخيص

من `frontend/`: شغّل `npm.cmd test -- --maxWorkers=1`، ثم `npm.cmd run test:browser`، و`npm.cmd run lint`، و`npm.cmd run build` (يتضمن TypeScript). عند فشل اختبار، اقرأ أول assertion: هل المشكلة عقد API، أم محتوى، أم تركيز؟ لا تعتبر worker startup timeout فشلًا وظيفيًا ولا تعتبره نجاحًا؛ أعد التشغيل وسجّل النتيجة الفعلية.

أُعيد إنتاج أخطاء المسار ونص التحميل والتركيز قبل إصلاحها. نتائج التشغيل النهائية موثقة في `docs/ai-sdlc/contracts/UI-06-REVIEW.md`. فحص Chromium يشمل أحجام شاشة مختلفة واستخدام لوحة المفاتيح، لكنه ليس شهادة WCAG أو اختبار جميع المتصفحات. تحذير حجم bundle موجود؛ تحسين تقسيمه عمل اختياري منفصل.

المتبقي: تنفيذ إجراء smoke test الموثق بموافقة صريحة، باستخدام ملفات وهمية وحسابات اختبار. لا نغلق sprint أو نبدأ Phase 3 قبل نجاحه ومراجعتك.

## أسئلة للفهم

1. لماذا يحتاج مسار المساعد إلى index route؟
2. لماذا نعيد التركيز إلى عنوان القائمة بعد الإزالة بدل زر الملف؟
3. ما الفرق بين فحص حجم الملف في الواجهة وفحصه في الخادم؟
4. لماذا لا نكرر طلب رفع تلقائيًا إذا انتهت مهلة الرد؟
5. ما الذي تثبته الاختبارات المضبوطة، وما الذي يحتاج اتصالًا حيًا لإثبات عزل المالكين؟

تمرين: في اختبار محلي فقط، اجعل تحديث القائمة بعد DELETE يفشل. تتبع رسالة الخطأ وتعطيل العمليات ثم نجاح Refresh. لا تستخدم بيانات Supabase الحية لهذا التمرين.
