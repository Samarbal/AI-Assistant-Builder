# ADR-001: Data Platform, Persistence, and Ownership Isolation

Status: accepted

## Context

The MVP must support multiple assistants per business owner, owner-scoped associated data, knowledge metadata, conversations, draft/published state, and semantic retrieval. The approved platform direction is Supabase.

## Decision

- Use Supabase as the preferred backend data platform.
- Use Supabase PostgreSQL for relational persistence.
- Use SQLAlchemy behind repository and service boundaries.
- Use Alembic for schema migrations.
- Use PostgreSQL with pgvector for stored knowledge vectors.
- Enforce owner-data isolation with both FastAPI owner-scoped operations and Supabase Row Level Security.
- Keep authentication as a separate concern, recorded in ADR-002.
- Use separate DATABASE_URL (restricted assistant_runtime) and
  MIGRATION_DATABASE_URL (Alembic only). Never fall back from one to the other.
- The runtime role cannot own application tables, bypass RLS, assume privileged
  roles, delete assistants, or update owner_id. Grant only required configuration
  UPDATE columns. Enable and force assistant RLS; deny direct anon/authenticated
  Data API access to this table without changing Supabase Auth.

## Alternatives considered

- SQLite or another local relational database: rejected because Supabase PostgreSQL is the approved MVP platform and the MVP requires hosted relational persistence with pgvector.
- PostgreSQL without Row Level Security: rejected because service-layer checks alone provide a weaker data-isolation boundary.
- A separate vector database: rejected because pgvector in the approved Supabase PostgreSQL platform satisfies the semantic RAG requirement without another data service.

## Rationale

This keeps relational data, ownership policies, migrations, and vectors within the approved Supabase platform while preserving clear application boundaries and a second database-level isolation control.

## Consequences

- The MVP depends on Supabase PostgreSQL and Supabase policy configuration.
- Repository and service interfaces keep application code testable and reduce direct database coupling.
- Schema changes must be represented through Alembic migrations.
- RLS policies and FastAPI owner checks must remain consistent.

## Risks / limitations

- Incorrect RLS policies or service-role usage could expose owner data.
- Supabase availability and configuration become operational dependencies.
- Migration drift between Alembic and the deployed database must be prevented.
