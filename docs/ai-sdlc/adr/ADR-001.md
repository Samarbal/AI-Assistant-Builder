# ADR-001: Data Platform, Persistence, and Ownership Isolation

Status: accepted

## Context

The MVP must support multiple assistants per business owner, owner-scoped associated data, knowledge metadata, conversations, draft/published state, and semantic retrieval. The approved platform direction is Supabase.

## Decision

- Use Supabase as the preferred backend data platform.
- Use Supabase PostgreSQL for relational persistence.
- Use SQLAlchemy behind repository and service boundaries.
- Use Alembic for schema migrations.
- Use PostgreSQL with pgvector for stored knowledge vectors.
- Enforce owner-data isolation with both FastAPI owner-scoped operations and Supabase Row Level Security.
- Keep authentication as a separate concern, recorded in ADR-002.
- Use separate DATABASE_URL (restricted assistant_runtime) and
  MIGRATION_DATABASE_URL (Alembic only). Never fall back from one to the other.
- The runtime role cannot own application tables, bypass RLS, assume privileged
  roles, delete assistants, or update owner_id. Grant only required configuration
  UPDATE columns. Enable and force assistant RLS; deny direct anon/authenticated
  Data API access to this table without changing Supabase Auth.

## Alternatives considered

- SQLite or another local relational database: rejected because Supabase PostgreSQL is the approved MVP platform and the MVP requires hosted relational persistence with pgvector.
- PostgreSQL without Row Level Security: rejected because service-layer checks alone provide a weaker data-isolation boundary.
- A separate vector database: rejected because pgvector in the approved Supabase PostgreSQL platform satisfies the semantic RAG requirement without another data service.

## Rationale

This keeps relational data, ownership policies, migrations, and vectors within the approved Supabase platform while preserving clear application boundaries and a second database-level isolation control.

## Consequences

- The MVP depends on Supabase PostgreSQL and Supabase policy configuration.
- Repository and service interfaces keep application code testable and reduce direct database coupling.
- Schema changes must be represented through Alembic migrations.
- RLS policies and FastAPI owner checks must remain consistent.

## Risks / limitations

- Incorrect RLS policies or service-role usage could expose owner data.
- Supabase availability and configuration become operational dependencies.
- Migration drift between Alembic and the deployed database must be prevented.

## Phase 4 addendum: public runtime and shared accounting (accepted for design)

The Phase 4 public data path uses a separate `assistant_public_runtime` login and
`PUBLIC_DATABASE_URL`; it never reuses `assistant_runtime`, migration credentials,
Supabase service-role credentials, or an owner identity fabricated for a visitor.
Both runtime logins are non-superuser, non-BYPASSRLS, NOINHERIT, non-owning roles
with no role memberships, no schema CREATE, and no direct cross-role assumption.
`assistant_runtime` keeps its existing owner-scoped grants and policies.

The public login receives only the required column-level SELECT/INSERT/UPDATE
privileges on publication, snapshot, source-reference, conversation and turn
objects, plus schema USAGE. It receives no direct privileges on the shared budget
ledger, original file metadata/text, Storage, draft mutation, indexing writes,
snapshot writes, function-owner role, or Supabase Data API. Exact per-object grants
and RLS predicates are specified in `docs/ai-sdlc/contracts/PHASE-0-CONTRACTS.md`.
Every new application table has ENABLE and FORCE RLS; policies fail closed on
missing or malformed transaction-local scope. All UPDATE policies have USING and
WITH CHECK. The public path is FastAPI-only; no grants are added to PUBLIC, anon,
authenticated or service_role.

Shared cost accounting is isolated in a non-exposed `ai_accounting` schema. A
dedicated `assistant_budget_executor` role is NOLOGIN, NOBYPASSRLS, owns no tenant
objects and can access only narrowly granted accounting tables under its own forced
RLS policies. Both runtimes have no ledger table grants. They may EXECUTE only four
fixed-signature SECURITY DEFINER functions for reserve, mark-dispatched, settle,
and cancel-undispatched operations. PUBLIC EXECUTE is revoked; the functions use
fixed `pg_catalog` search_path, schema-qualified object names, no dynamic SQL, and
verify `session_user` against the two allowed runtime logins. They atomically check
operation, attempt and UTC-day caps and maintain idempotent reservations. They do
not read or write tenant tables.

The accounting functions do not turn caller-set PostgreSQL settings into trusted
authentication. FastAPI remains responsible for validating Supabase Auth and setting
owner or visitor context. This follows the existing ADR-002 trusted-application
boundary; arbitrary SQL under a runtime credential remains outside the protection
provided by a custom session variable. The ledger protects concurrent spend and
prevents direct runtime counter edits, not a compromised application that lies
about provider usage. Pricing and provider billing semantics must be verified before
paid dispatch is enabled.
