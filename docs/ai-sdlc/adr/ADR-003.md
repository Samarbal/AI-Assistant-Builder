# ADR-003: Knowledge Storage, Processing, and Semantic RAG

Status: accepted

## Context

The MVP grounds assistant responses in business knowledge supplied as PDF and DOCX files. It must support file management, semantic retrieval, conservative fallback behavior, and owner/file isolation without OCR.

## Decision

- Store original knowledge files in private Supabase Storage.
- Store file metadata and processing state in Supabase PostgreSQL.
- Allow at most 5 knowledge files per assistant.
- Limit each file to 10 MB.
- Support PDF and DOCX only.
- Use focused PDF and DOCX processors; do not implement OCR.
- Treat malformed, encrypted, scanned, empty, and unsupported documents as failed processing and exclude them from retrieval.
- Extract text, chunk it at approximately 600 tokens with 100-token overlap, and retain assistant/file ownership metadata on each chunk.
- Store embeddings and searchable vectors in PostgreSQL with pgvector.
- Retrieve the top five semantic matches through a narrow Retriever interface.
- Keep the minimum similarity threshold configurable and calibrate its initial value with representative known-answer and unknown-answer fixtures.
- If no retrieved chunk passes the relevance boundary, return the configured fallback without business-specific generation.
- Issue short-lived signed URLs only when an authenticated owner needs access to a stored file.

## Alternatives considered

- Local filesystem storage: rejected because Supabase Storage is the approved file platform.
- OCR and broad document conversion: rejected because OCR is outside the MVP.
- SQLite full-text search: rejected because the approved MVP must demonstrate semantic RAG.
- A separate managed vector database: rejected because pgvector in Supabase PostgreSQL is approved and avoids another service.

## Rationale

This provides semantic RAG while keeping files, metadata, vectors, and ownership within the approved Supabase platform. Explicit processing states and a conservative threshold prevent unusable or weakly relevant content from producing fabricated business answers.

## Consequences

- Changing the embedding model requires controlled reindexing of stored vectors.
- Chunking and threshold values are configuration and validation concerns rather than owner-facing features.
- File processing must distinguish stored files from ready-to-retrieve knowledge.
- Private storage and signed URLs add authenticated access steps for owner file viewing.

## Risks / limitations

- PDF/DOCX extraction quality can be poor for scanned or complex documents; those files fail safely in the MVP.
- The initial similarity threshold is not a universal accuracy guarantee and requires fixture-based calibration.
- Embedding API availability, cost, quota, and vector-dimension compatibility must be validated before implementation is finalized.
