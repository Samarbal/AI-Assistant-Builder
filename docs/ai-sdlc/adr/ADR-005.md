# ADR-005: Publishing, Public Widget, and Public Access Security

Status: accepted

## Context

Owners edit assistants and knowledge privately, then publish a public version for a JavaScript website widget. Public requests must never use draft state or expose owner-only data. The MVP is a single-instance deployment with simple rate limiting.

## Decision

- Keep a mutable owner-visible draft.
- Create an immutable published snapshot on publish/update.
- Atomically activate the new published snapshot.
- Preserve the previous published snapshot for recovery.
- Removing a draft knowledge attachment releases its draft slot but must not remove
  immutable artifacts referenced by retained snapshots. Reference-aware physical
  cleanup is required before publishing is enabled; no snapshot implementation is
  introduced by Phase 2 Step 1.
- Use a generic JavaScript widget with an opaque public assistant identifier.
- Route widget requests through the FastAPI public chat boundary.
- Resolve public requests only to the active published snapshot.
- Never expose draft configuration, owner data, or owner credentials through public endpoints.
- Use simple in-process rate limiting for the single-instance MVP, initially approximately 30 requests per minute per IP/assistant pair, with the value configurable.

## Alternatives considered

- Mutating the public assistant record in place: rejected because draft changes must remain private until publish/update.
- Separate widget and public-chat deployment: rejected because it adds infrastructure and release coordination outside the portfolio MVP.
- No public rate limiting: rejected because unauthenticated widget traffic needs a basic abuse boundary.
- Distributed rate limiting: deferred because the MVP is single-instance and does not require horizontal scaling.

## Rationale

Immutable published snapshots make draft/public separation explicit, preserve a rollback target, and allow the widget to remain a simple generic asset. The in-process limiter is proportionate to the single-instance MVP while leaving a migration path for a distributed deployment.

## Consequences

- Publishing requires an atomic snapshot and active-version transition.
- Public chat uses published knowledge and configuration only.
- Failed publishing leaves the prior published snapshot active and the modified draft available for retry.
- The opaque public identifier must not reveal owner identity or draft state.
- Rate limiting is process-local and not a multi-instance security boundary.

## Risks / limitations

- Snapshot/index synchronization must be tested carefully, especially after knowledge removal or reindexing.
- An opaque identifier is not an authorization mechanism for owner APIs; owner access still requires Supabase Auth and RLS.
- In-process rate limits reset on restart and do not coordinate across instances.

## Phase 4 addendum: visitor API and accounting boundary

- Each assistant keeps a mutable owner draft and immutable published snapshots.
  Publishing snapshots the saved behavior, public appearance, fallback, ready index
  identity and complete source manifest. Zero attached files may publish as a
  fallback-only snapshot. Any attached file still processing or failed blocks
  publishing. Playground use remains optional.
- Publication atomically activates a snapshot and preserves all previous snapshots
  and their referenced index/source artifacts. Public retrieval uses the snapshot's
  pinned source set, regardless of later draft edits, removals, or reindexing.
- A visitor conversation capability is random, stored only as a digest, scoped to
  one conversation/public assistant, and expires 24 hours after creation without
  sliding renewal. Turns are independent: the conversation is recorded for owner
  history but prior messages are not model context. A turn pins one active snapshot.
  If that version changes before the answer commits, return a conflict and never
  retry the paid generation automatically.
- Public responses omit citation identifiers, filenames and excerpts. Evidence
  validation remains server-side. Public identity/config responses contain only
  published display data. Public IDs are identifiers, not credentials for owner APIs.
- Deliver the generic widget through a JavaScript loader and isolated iframe.
  The frame keeps its conversation capability in memory and sends it in a request
  header; it does not pass tokens or chat text to the embedding page. Keep owner
  cookies/session out of public chat. Render plain text and preserve the existing
  configurable 30 requests/minute per IP/public-assistant rate boundary.
- Use separate `assistant_public_runtime` database credentials and RLS policies.
  The role sees active published projections and referenced chunks, and narrowly
  writes conversations/turns. It cannot read drafts, original knowledge-file
  metadata/text, Storage, or owner history beyond the current assistant's records.
  Owner operations remain on `assistant_runtime`.
- Enforce durable shared reservations across indexing, owner Playground and public
  chat. Initial caps are $0.01/message, $0.10/index and $1 per UTC day, subject to
  provider price/quota verification. A reservation covers the maximum bounded input
  and output cost before dispatch. Unknown cost, missing usage, ledger errors, or an
  uncertain dispatch fail closed; uncertain charges remain reserved and no automatic
  retry is allowed. The fixed accounting functions cannot read tenant data and the
  runtime roles have no direct ledger privileges.
- Draft edits, publication, public finalization and physical cleanup use a
  consistent lock protocol. Cleanup first claims an artifact, then verifies no
  retained snapshot references it. Publication rejects missing or cleanup-claimed
  sources. Recovery schema checks remain exact and fail closed until updated with
  the approved snapshot/accounting objects.

The exact role, grant, policy and function design plus P4-02 implementation/test
sequence are recorded in `docs/ai-sdlc/contracts/PHASE-0-CONTRACTS.md` and
`docs/ai-sdlc/plans/PLAN-001.md`. This addendum does not authorize migrations,
live database changes, deployment or public enablement. Public rate limiting remains
process-local as approved for the single-instance MVP; a multi-instance deployment
would need a separate design decision.

## P4-06 implementation addendum: widget hosting and browser boundary

- The existing React/Vite frontend hosts the generic `widget.js` loader and the
  public `/widget` iframe route. FastAPI does not serve frontend assets.
- FastAPI allows browser CORS only for the public chat route family and only from
  the exact configured `WIDGET_ASSET_ORIGIN`. Wildcard origins and credentialed
  CORS are forbidden. Allowed methods are GET/POST and the required request headers
  are `Content-Type`, `X-Demo-Access`, and `X-Visitor-Token`.
- Owner APIs remain same-origin and receive no widget CORS headers. Their Supabase
  bearer token, database role, and RLS behavior are unchanged.
- A tester enters the server-issued demo access code into the iframe. The code is
  held only in frame memory and sent as `X-Demo-Access`; it is never placed in the
  embed snippet, URL, browser storage, or parent-page DOM. The visitor conversation
  capability is also memory-only and sent as `X-Visitor-Token`.
- Public chat remains disabled by default and retains the server-side two-tester
  gate. This addendum does not enable chat or integrate shared budget dispatch.
