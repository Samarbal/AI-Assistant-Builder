# ADR-005: Publishing, Public Widget, and Public Access Security

Status: accepted

## Context

Owners edit assistants and knowledge privately, then publish a public version for a JavaScript website widget. Public requests must never use draft state or expose owner-only data. The MVP is a single-instance deployment with simple rate limiting.

## Decision

- Keep a mutable owner-visible draft.
- Create an immutable published snapshot on publish/update.
- Atomically activate the new published snapshot.
- Preserve the previous published snapshot for recovery.
- Use a generic JavaScript widget with an opaque public assistant identifier.
- Route widget requests through the FastAPI public chat boundary.
- Resolve public requests only to the active published snapshot.
- Never expose draft configuration, owner data, or owner credentials through public endpoints.
- Use simple in-process rate limiting for the single-instance MVP, initially approximately 30 requests per minute per IP/assistant pair, with the value configurable.

## Alternatives considered

- Mutating the public assistant record in place: rejected because draft changes must remain private until publish/update.
- Separate widget and public-chat deployment: rejected because it adds infrastructure and release coordination outside the portfolio MVP.
- No public rate limiting: rejected because unauthenticated widget traffic needs a basic abuse boundary.
- Distributed rate limiting: deferred because the MVP is single-instance and does not require horizontal scaling.

## Rationale

Immutable published snapshots make draft/public separation explicit, preserve a rollback target, and allow the widget to remain a simple generic asset. The in-process limiter is proportionate to the single-instance MVP while leaving a migration path for a distributed deployment.

## Consequences

- Publishing requires an atomic snapshot and active-version transition.
- Public chat uses published knowledge and configuration only.
- Failed publishing leaves the prior published snapshot active and the modified draft available for retry.
- The opaque public identifier must not reveal owner identity or draft state.
- Rate limiting is process-local and not a multi-instance security boundary.

## Risks / limitations

- Snapshot/index synchronization must be tested carefully, especially after knowledge removal or reindexing.
- An opaque identifier is not an authorization mechanism for owner APIs; owner access still requires Supabase Auth and RLS.
- In-process rate limits reset on restart and do not coordinate across instances.
