# ADR-004: AI Generation and Embedding Integration

Status: accepted

## Context

The MVP needs grounded answer generation and semantic embeddings, but owners must not configure AI model parameters. The selected generation service exposes an OpenAI-compatible API. The implementation must remain replaceable without adding multi-provider routing.

## Decision

- Keep answer generation behind a narrow `AnswerGenerator` abstraction.
- Use the selected OpenAI-compatible API provider for text generation through one provider adapter.
- Configure the provider base URL, API key, and model name through environment variables (for example, `AI_BASE_URL`, `AI_API_KEY`, and `AI_MODEL`); never hardcode them.
- Keep provider credentials out of source control and server-side only.
- Do not expose provider, base URL, API key, or model configuration through the business-owner product UI or API.
- Keep the adapter replaceable so another OpenAI-compatible provider can be substituted without changing the application or domain layer.
- Keep embedding generation behind a narrow embedding abstraction.
- Keep embedding provider and model selection separate from the generation provider decision.
- Select one embedding provider and model for the MVP; do not use multiple embedding providers.
- Keep provider credentials server-side and normalize timeout, quota, malformed-response, and provider-failure behavior.
- Track the embedding provider/model, vector dimension, and embedding/index version for indexed knowledge.
- Never mix vectors produced by incompatible embedding models or dimensions in the same active retrieval space.
- When the embedding model changes, regenerate embeddings for the affected knowledge corpus into a new controlled index/version.
- Do not partially replace the active retrieval space during reindexing.
- Activate the new index/version only after reindexing succeeds and validation passes.
- Preserve a safe rollback path to the previous valid index/version where practical.

## Alternatives considered

- Multi-provider routing: rejected because it adds scope and operational complexity without an MVP requirement.
- Local generation or embedding models: rejected because they add runtime, hardware, and packaging risk within the 4.5-week schedule.
- Hardcoding one provider or model in the application: rejected because the provider must remain configurable and replaceable.

## Rationale

One provider implementation and two narrow interfaces keep the application simple while preserving a controlled replacement point. Environment-based configuration allows the selected OpenAI-compatible provider or another compatible provider to be used without changing domain logic.

## Consequences

- The MVP depends on the availability and compatibility of the selected OpenAI-compatible generation provider.
- Provider-specific request details stay inside adapters.
- Provider base URL, API key, and model name are deployment configuration, never product configuration.
- Embedding/index metadata is tracked so incompatible vector spaces cannot be mixed.
- Reindexing creates a new controlled index/version before activation; the active retrieval space is not partially replaced.
- Owners see configured assistant behavior, not provider or model controls.

## Risks / limitations

- Provider availability, quota, latency, compatibility, and usage terms may change.
- Generation quality may be insufficient for some business documents even when retrieval succeeds.
- Embedding compatibility and retrieval quality must be verified with representative fixtures.

## Implementation-time validation items

- Exact generation model: intentionally unresolved until an OpenAI-compatible provider smoke test validates grounded-answer quality, context capacity, latency, availability, quota, and usage terms.
- Exact embedding provider and model: intentionally unresolved until one provider/model is selected and validated before knowledge indexing begins; it remains independent from the generation provider.
- Vector dimension: intentionally unresolved until the embedding model is selected; it must match that model and be recorded before production knowledge vectors are created or indexed.
- Controlled reindex implementation details: the policy is decided above, while operational details may be finalized when knowledge indexing is implemented.
- Numeric similarity threshold: intentionally unresolved; it remains configurable and must be calibrated with the Phase 0 known-answer and unknown-answer fixtures before grounded retrieval is finalized.
